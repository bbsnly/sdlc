## Introduction

This guide takes a project that runs `sdlc` 0.6.1 to 0.7.1. There is no 0.7.0
release, so 0.7.1 is the next one up.

Nothing in your configuration is refused by the new release, so the update
itself is short. What changes is how a story is worked:

- A new agent, the test reviewer, reads the tests before they are frozen.
- `sdlc` runs your build, tests and checks itself, once, when the code is
  written. Nobody runs them again while the work is unchanged.
- The loop decides implementation questions itself and writes each one down.
  It stops for you only on questions about the product.
- A story can wait for your approval because of the files it touches, and not
  only because of its risk tier.
- The slash commands that are yours alone, such as `/sdlc:approve`, run again
  in the Code tab of Claude Desktop.

There is one setting worth adding straight away, and a few more you may want.
You make every such edit on trunk, in your main checkout, between stories,
because [no story lands a change](../configuration.md#changing-a-setting) to
`.sdlc/config.json`.

## Before you update

The simplest course is to land the stories that are under way first. A story
you leave under way carries on under the new rules, with the configuration
its worktree started with.

Two things outside your project are worth a minute before you update. Both
are about the six commands only you may run: `/sdlc:approve`,
`/sdlc:unfreeze`, `/sdlc:ack`, `/sdlc:remap`, `/sdlc:release` and
`/sdlc:assign`. The hook now runs one only where it can tell that you typed
it, in a session you are at.

### Update Claude Code

Update Claude Code, or Claude Desktop, to its newest release. The hook's check
is known to work with Claude Code 2.1.321 in Claude Desktop. With an older
one, a slash command may answer that it did not run, and say to update.

### Take three variables out of your environment

If you set `AI_AGENT`, `CLAUDE_CODE_EXECPATH` or `GIT_EDITOR=true` yourself,
take it out. Look in the shell profile of the terminal you start Claude Code
from, and in Claude Desktop's
[local environment editor](../claude-desktop.md#set-variables-in-the-local-environment-editor).
Then open a new session.

The hook reads all three to tell a command you typed from an agent's. With
any of them set where you start your session, every slash command of yours
answers that it did not run, and names the variable. Any other value of
`GIT_EDITOR` is fine.

## Update the command and the plugin

Update both parts together. This matters more than usual: the test reviewer
comes with the plugin, and the new `sdlc freeze` waits for a review that the
old plugin has no agent to make.

First the command, in a terminal:

```console
$ npx @bbsnly/sdlc@latest install
```

Then the plugin, in Claude Code:

```text
/plugin update sdlc@sdlc
```

Restart Claude Code, so that it loads the plugin's new hooks.
[Updating](../installation.md#updating) covers a command you installed
another way.

## After you update

With the new `sdlc` installed, there are four things to look at in your
project. Only the first is an edit most projects should make.

### Set the narrow test command

`sdlc freeze` now runs the story's new tests before it freezes them, to see
them fail. `commands.test_files` is the command it runs: your test runner,
given only the files a story adds or changes. `sdlc` names a file that lists
them in `SDLC_TEST_FILES`.

A project set up before 0.7.1 has no such command. Don't worry: nothing is
refused, and the freeze runs the whole of `commands.test` in its place. That
works, and it costs you the whole suite at every freeze.

For Go, add this to `commands` in `.sdlc/config.json`. It tests the packages
that hold the files listed:

```json
"test_files": "if [ -n \"${SDLC_TEST_FILES-}\" ]; then sed -e 's#^#./#' -e 's#/testdata/.*#/x#' -e 's#/[^/]*$##' \"$SDLC_TEST_FILES\" | tr '\\n' '\\0' | xargs -0 go test -count=1; else go test ./... -count=1; fi"
```

[The narrow test command](../configuration.md#the-narrow-test-command) has
the command for Python, Rust and Node, and says what a command of your own
has to do. Then check the file and commit it on trunk:

```console
$ sdlc doctor
$ git add .sdlc/config.json
$ git commit -m "Add the narrow test command"
```

> [!WARNING]
> Read `.sdlc/stories/<ID>/freeze-run.log` after the first story's freeze. The
> freeze expects the run to fail, so a command that fails for a reason of its
> own looks the same as tests that fail as they should.

### Put what your commands need in the configuration

`sdlc` now runs `build`, `test`, `lint`, `fmt_check`, `coverage` and
`mutation` itself, and what it records stands in for every later run. So the
hook [refuses a command line](../enforcement.md#commands-run-as-configured)
that sets anything in front of `sdlc gate implementation pass` or
`sdlc freeze`, such as `GOFLAGS=... sdlc gate implementation pass`.

If your commands pass only when a session sets a variable first, put the
variable in the command itself:

```json
"test": "GOWORK=off go test ./... -count=1"
```

Check one more thing while you are there. None of the six commands may write
a file into the project that git does not ignore. A run that does
[records nothing](../troubleshooting.md#sdlc-e0095), and the refusal names
the file. Have the command write under `$SDLC_RUN_DIR`, which
[Share one test run with coverage](#share-one-test-run-with-coverage)
describes, or to a path git ignores.

### Untrack files that git also ignores

A finished story now lands on the result Gate 5 recorded, without running
your commands again. A file git tracks that `.gitignore` also matches defeats
that. List such files, from your main checkout:

```console
$ git ls-files -ci --exclude-standard
```

If that prints nothing, you are done. Otherwise untrack each file it names
with `git rm --cached <file>`, or stop ignoring it, and commit. With such a
file left in place nothing breaks, but every landing runs your commands
again.

### Decide who reviews the tests

The test reviewer is on by default, in every project, whether or not your
`team` section names it. You may leave it as it is, and most projects should.
[Tests are reviewed before they are frozen](#tests-are-reviewed-before-they-are-frozen)
says what it does.

To keep Gate 3 as it was, turn the agent off:

```json
"team": {
  "agents": {
    "test-reviewer": { "enabled": false }
  }
}
```

To keep the review but not let it stop the freeze, set `"can_block": false`
on the same entry in place of `enabled`. The freeze then waits only until the
reviewer has reviewed.

## What behaves differently

None of these needs an edit. They are here so that nothing surprises you in
your next story.

### Tests are reviewed before they are frozen

At Gate 3, the test reviewer reads the new tests against your acceptance
criteria and the analysis, and runs them. It blocks on a test that contradicts
a criterion, a criterion no test would catch, or a test that passes for the
wrong reason. Its block goes back to the test author while a test can still
change. After the freeze, the same mistake would cost you an unfreeze.

`sdlc freeze` [waits for its approval](../troubleshooting.md#sdlc-e0029) of
the tests as they are, so a test changed, added or renamed after the approval
is reviewed again. `sdlc review list` shows where the review has got to:

```console
$ sdlc review list --gate tests_frozen
Review policy: REVIEW.md
  tests_frozen    test-reviewer   blocking  not reviewed
```

[The test reviewer](../the-agents.md#gate-3-the-test-reviewer) describes the
agent.

### The freeze runs the new tests

Before it freezes them, `sdlc freeze` runs the new and changed tests and
expects them to fail, because a test written before its code fails until the
code exists. The last line it prints says so:

```text
  commands.test_files ran over the new and changed test files and failed with status 1, as new tests do; its output is in /home/<user>/src/billing/.sdlc/stories/AUTH-3/freeze-run.log
```

New tests that pass test nothing yet, so
[the freeze is refused](../troubleshooting.md#sdlc-e0085), and the test
author makes each one fail for the reason it is there.

### Your commands run once, at Gate 5

Under 0.6.1 your suite ran up to four times in a story: for the implementer,
the verifier, the freeze and the landing. Now `sdlc` runs your commands
itself when the implementation is recorded as done, in this order, those that
are set: `build`, `test`, `lint`, `fmt_check`, `coverage` and `mutation`.

While the work stays as it was for that run, nobody runs them again. The
verifier works from the result, and the landing lands on it. A story that was
put onto a trunk that had moved still has them run again at the landing.

A command that fails, misses its threshold or prints no figure
[fails the gate](../troubleshooting.md#sdlc-e0095), and that counts towards
`loop.max_rework_rounds` like any other failed gate. Everything the commands
printed is kept in `.sdlc/stories/<ID>/implementation-run.log`.

### The loop asks you less

Under 0.6.1 the loop handed you every question an agent raised. It now tells
[two kinds of decision](../the-loop.md#two-kinds-of-decision) apart:

- **A product decision is yours.** It is about what the story's user sees or
  can do, or what is in the story's scope. The loop tries to stop only once
  for these: at Gate 2 it hands you the story as a `product_decision`, with
  every product question the analysis found, each with options and a
  recommendation.
- **An implementation decision is the loop's.** How an edge case behaves,
  which of two designs meets the criteria, an internal name. The agent that
  raised the question recommends an answer, and the loop applies it and
  carries on.

Every decision the loop makes is written down, in
`.sdlc/stories/<ID>/DECISIONS.md`, and `sdlc log` lists each with its story
once the story has landed:

```text
  decided    analysis by researcher: "Is a token that expires this very second expired?" -- chose "expired", because "the check runs after the instant it names"
```

So read the log as you did, and mark it read as you did:

```console
$ sdlc ack --through HEAD
```

Until you do, `sdlc status` has a `Decisions:` line that counts the ones you
have not acknowledged. If you disagree with a decision, send the story back.

> [!NOTE]
> Nothing in `sdlc` sorts a question into its kind. The agents judge each one,
> which is why every decision is put in front of you afterwards.

### A reviewer that keeps blocking goes to an arbiter

Under 0.6.1, a reviewer that blocked as often as `loop.max_review_rounds`
allows, twice by default, handed the story to you. Now the gate goes to that
reviewer's arbiter first: a fresh agent of the same kind, which has seen none
of the argument and rules on each open finding. Its review stands in the
reviewer's place, and `sdlc review list` says whose it is:

```text
  design_review   architect       blocking  approve (by architect-arbiter, round 1)
```

The story is handed to you only when the arbiter has blocked to the same
limit too. An arbiter is asked for one step above its reviewer: the next
effort in `team.efforts`, or the next model where the effort is already the
highest. A reviewer you have disabled has no arbiter, and its limit hands the
story to you as before. [The arbiter](../the-loop.md#the-arbiter) has the
details.

### Every commit says whether it waited for you

Before the commit, `sdlc status` in a story's worktree now has a `pause` line.
It says whether the commit will wait for your approval, and why:

```text
  pause  the commit will not pause: the story's risk tier is low, which pre_commit_pause_tiers does not pause; pre_commit_pause_paths lists no path
```

Afterwards, `sdlc log` shows a `no pause` line for every story that was
committed without your approval, until your `sdlc ack` covers it. That is so
in every project, whether or not you
[list any paths](#pause-for-the-paths-a-story-touches).

### Your slash commands in Claude Desktop

Since Claude Code 2.1.312, the hook took a slash command typed in the Code
tab of Claude Desktop for an agent's, and refused it. Your six commands run
there again.

Where the hook still cannot tell that you typed one, its answer reads
differently. It begins like this, and goes on to name each variable it could
not read and what to do about it:

```text
/sdlc:approve did not run: the hook could not tell that a person typed it:
```

In Claude Desktop, you may always type the command on a line that starts with
`!` instead, such as `!sdlc approve <ID>`.
[A slash command did not run](../troubleshooting.md#a-slash-command-did-not-run)
lists each reason.

Your agent is held a little more tightly for the same reason. The hook
[refuses a command](../enforcement.md#enforcement-stays-on) that sets or
removes one of the variables it reads. An agent that puts `GIT_EDITOR=true`
in front of a git command is refused, and runs it without the setting. The
hook also refuses more ways of starting a second Claude Code session from
inside one.

## Settings you may want to add

Each of these is off until you add it. Make the edit on trunk, run
`sdlc doctor`, and commit.

### Pause for the paths a story touches

A risk tier is a word somebody chose when the story was written. The files a
change touches are what it does. `human_gates.pre_commit_pause_paths` lists
patterns for files, and a story whose change touches one waits for your
approval before it is committed, whatever its tier:

```json
"human_gates": {
  "pre_commit_pause_tiers": ["high"],
  "pre_commit_pause_paths": ["src/auth/**", "install.sh"]
}
```

Write each pattern from the repository root, with `/` between its parts. `*`
does not cross a `/`, `**` stands for any number of directories, and a bare
directory covers everything under it. Case is ignored. A pattern `sdlc`
cannot use is [refused](../troubleshooting.md#sdlc-e0045) when the file
loads, and the refusal names it.

List the files where a mistake costs the most, such as your authentication,
your payments or your migrations, and little else. A file that nearly every
story touches would pause nearly every story. A changed, moved, deleted or
new file all count, and a story cannot take its own pause away by editing its
copy of the configuration.

> [!WARNING]
> Keep `pre_commit_pause_tiers` as it is until every machine that works the
> project runs 0.7.1 or newer. An older `sdlc` ignores the paths, so with the
> tiers emptied it would pause nothing.

[The pause before the commit](../guides/human-approval-gates.md#the-pause-before-the-commit)
shows what the pause looks like and how to answer it.

### Share one test run with coverage

Each run of your commands is handed a new, empty directory outside your
project, in `SDLC_RUN_DIR`. `test` may leave its coverage data there and
`coverage` may read it, so that the suite runs once and not twice.

You need not change anything: a `coverage` command that runs the suite itself
still works. [The run directory](../configuration.md#the-run-directory) has
the pair of commands for Go, Python, Rust and Node.

### Give one reviewer its own limit

`max_rounds` in an agent's entry sets how many times that reviewer may block
before its gate goes to the arbiter. An agent without one keeps
`loop.max_review_rounds`:

```json
"team": {
  "agents": {
    "architect": { "max_rounds": 3 }
  }
}
```

### Say whether the loop may add a dependency

Which open-source dependency to use is an implementation decision, where your
contract allows it. A new project's contract says, under "Allowed
dependencies", that the loop may add one whose licence the project's licence
check accepts.

No command rewrites a contract you already have. If you want the loop to
choose, or never to, say so in the `## SDLC Contract` section of your
`CLAUDE.md`, and commit it on trunk.

## If a script reads sdlc's output

Check these if you have a script or a CI job built on what `sdlc` prints:

- **`sdlc status --json`** gains `decisions_unread`, which is always there,
  and for a story under way `pre_commit_pause` and `commands`.
- **`sdlc log`** gains `no pause` and `decided` lines, and
  `landed_without_pause` and `decisions` in `--json`.
- **`sdlc review add --json`** gains `arbiter`, and
  **`sdlc review list --json`** gains `gone_to` and `reviewed_by`.
- **A reviewer's block at its limit** no longer ends the iteration. A script
  that waited for the hand-over now sees the gate go to the arbiter.
- **`sdlc freeze`** begins its refusals over a review with a new first line,
  `the freeze waits for the test reviewer's review of the tests as they are`.
- **The refusal of [a commit that waits for you](../troubleshooting.md#sdlc-e0037)**
  names each file and the pattern it matched, as well as the tier. So does
  the refusal of [a landing that met a conflict](../troubleshooting.md#sdlc-e0075).
- **`sdlc gate implementation pass`** takes as long as your commands do, and
  prints one line on standard error before each. A script that ran the
  commands afterwards to the same end can stop.
- **`sdlc decide`** is a new command, and `SDLC-E0094` and `SDLC-E0095` are
  new codes.

## Also fixed

You need do nothing about these:

- Two plain `sdlc start`s in two checkouts at the same moment no longer leave
  one refused. The one that waited takes the next story.
- On Windows, a quick command at the landing, the implementation gate or the
  freeze is no longer refused with "Access is denied".
- With `freeze.allow_new_test_files` on, on macOS or Windows, adding a test
  after renaming a frozen one only by its case no longer gets stuck.

## Check it worked

First, make sure the command is the new one, in a new terminal:

```console
$ sdlc version
```

Then check your project, from its root:

```console
$ sdlc doctor
```

Its last line reads `Everything checks out.`, and its `commands` line lists
`test_files` once you have set it.

Next, type `/sdlc:next` in Claude Code and let a story begin. From the
story's worktree, two commands show the new release at work:

```console
$ sdlc review list --gate tests_frozen
$ sdlc status
```

The first lists `test-reviewer`, unless you turned it off. The second has a
`pause` line under `next`.

Last, once that story has landed, read `sdlc log`, and mark it read with one
of your own commands. Type `/sdlc:ack --through HEAD` in Claude Code, or in
the Code tab of Claude Desktop. It answers `Acknowledged through`, with the
commit.
