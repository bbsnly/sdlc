# Migrating from `v0.5.0` to `v0.6.0`

Update the `sdlc` binary and the plugin together, as
[Updating](../installation.md#updating) says: an old binary beside the new plugin does not know
the new flags, and answers `SDLC-E0034` for them. Do the configuration edits below on trunk,
between stories, because a story cannot carry a change to `.sdlc/`.

## `fix(cli)!: take only a ready story on a bare sdlc start` (`54af2b2`)

Commit `54af2b23e2526843c7e09b424dd64b918f5ac88e`.

### What changed

A bare `sdlc start` used to take `todo` and `ready` stories alike. It now takes `ready` stories
only. A project whose stories are all `todo` gets `SDLC-E0010` and exit 1 from a bare
`sdlc start`, and `sdlc status` and `sdlc story list` name no next story. Naming a `todo` story
with `sdlc start <ID>` still starts it, and resuming a story under way is unchanged.

### Steps

1. In the backlog file named by `backlog.path`, set `status` to `ready` on each story whose
   criteria are settled and that you want picked next.
2. Or leave the backlog as it is and name the story each time: `sdlc start <ID>`.
3. If a script or a habit relies on a bare `sdlc start` taking a `todo` story, change it to name
   the story.

### Verify

```console
$ sdlc story list
```

The next story is named once one is `ready`, and `sdlc start` with no id takes it. With only
`todo` stories left, `sdlc start` exits 1 with `SDLC-E0010`, says how many it passed over and
names up to five.

## `feat(cli)!: say when a gate's agents' time passes budget.gate_hours` (`11673ae`)

Commit `11673ae3673ff4d6fb4434b543edd87915ca7676`.

### What changed

`budget.gate_hours` is a new optional setting: hours of the agents' time each gate may take,
by gate key. Past the number, `sdlc gate`, `sdlc review add` and `sdlc status` print one line on
stderr, and decide, print on stdout and exit as before. A bad value or a key that is not a gate
key is refused with `SDLC-E0045`, and `sdlc doctor` now ends the configuration detail of every
`SDLC-E0045` cause with `(SDLC-E0045)` after a space. Nothing is turned on until you add the
setting.

### Steps

1. Optional: add `gate_hours` to `budget` in `.sdlc/config.json`, with a gate key from `dor`,
   `analysis`, `tests_frozen`, `plan`, `design_review`, `implementation`, `verification`,
   `verifier_review`, `code_review`, `commit` and `retro`, and a number of hours:

   ```json
   "budget": {
     "per_story_usd": 60,
     "gate_hours": { "tests_frozen": 2, "implementation": 3 }
   }
   ```

2. Remove the setting, or set a gate's number to `0`, to silence it.
3. If a script matches the configuration detail of `sdlc doctor` for `SDLC-E0045`, allow the
   added suffix.

### Verify

```console
$ sdlc doctor
```

It exits 0. A negative number, a value that is not a number, or a key that is not a gate key is
named with its entry and `SDLC-E0045`.

## `feat(cli)!: show a stale Gate 4 reviewer what changed since its review` (`6a88c57`)

Commit `6a88c57a7f36a6133d3e3b44f16ccce09164a0aa`.

### What changed

`sdlc artifact write plan` now keeps each plan revision under the story's `plans/<sha256>.md`,
and the new `sdlc artifact diff plan --since <role>` prints what changed since that design
reviewer's latest review. A revision that does not match its name is refused with `SDLC-E0084`
and the reviewer reads the whole plan. `sdlc review list` names the revision on the stale line
of a design review, and `sdlc review list --json` gives it as `reviewed_subject`.

### Steps

1. Nothing to change in the configuration or the backlog.
2. If a script reads the stale line of `sdlc review list`, or the JSON of
   `sdlc review list --json`, allow the revision name on that line and the new
   `reviewed_subject` key.
3. Staleness and the gate's wait are unchanged. The Gate 4 runbook in the new plugin asks a
   stale reviewer to look at the diff, so update the plugin with the binary.

### Verify

```console
$ sdlc review list
$ sdlc artifact diff plan --since architect
```

On a story with a stale design review, the first names the revision the review was stamped
with, and the second prints a unified diff from it to the current `PLAN.md`.

## `feat(cli)!: run commands.freeze_check before sdlc freeze hashes` (`4a023d2`)

Commit `4a023d2fc4168b1c4902f75aee0d239dbc7f6f38`.

### What changed

`commands.freeze_check` is a new command that `sdlc freeze` runs before it records anything,
with `SDLC_FREEZE_FILES` naming the new or changed test files, one per line. A check that
fails, or that changes a test file, takes no freeze and is refused with `SDLC-E0085`. It is empty
by default, so `sdlc freeze` does what it did until you choose one. `sdlc init` writes the key
into a new config, `sdlc doctor` prints a `freeze check` line, and `sdlc doctor` no longer calls
a shell builtin such as `continue`, `local` or `wait` a program that is not installed, so it exits
0 on a command that used to make it exit 1.

### Steps

1. Optional: add a check to `commands` in `.sdlc/config.json`, one that fails on a test file CI
   would refuse. The Go lint is a common choice:

   ```json
   "commands": {
     "freeze_check": "golangci-lint run ./..."
   }
   ```

2. Quote each name in `SDLC_FREEZE_FILES` and never evaluate it: it is the test author's data.
3. The check runs with your permissions and without a prompt, so read it in a repository you
   did not write.

### Verify

```console
$ sdlc doctor
```

The `freeze check` line says whether `commands.freeze_check` is set, never what it holds, and
`doctor` exits 0. On the next `sdlc freeze` the freeze event records that the check ran and
passed.

## `feat(cli)!: remove sdlc parallel` (`d509fcd`)

Commit `d509fcd6ce87d425a5fdd7e149df3c0715c6871d`.

### What changed

`sdlc parallel` is an unknown command, with its configuration section and its hook rule.
`SDLC-E0057` to `SDLC-E0066` are retired. A `parallel` key left in `.sdlc/config.json` changes
nothing, but `sdlc doctor` reports it as a setting it does not know and exits 1. An older binary
still runs the command, so update it along with the plugin.

### Steps

1. Delete the `parallel` section from `.sdlc/config.json` and commit the change on trunk.
2. To work several stories at once, start each with `sdlc start <ID>`, or `/sdlc:next <ID>` in a
   session in the main checkout, and open a session in each story's worktree.
3. Replace any script that ran `sdlc parallel` with those two steps.

### Verify

```console
$ sdlc doctor
```

It exits 0 and names no `parallel` setting. `sdlc parallel` answers that the command is unknown.

## `feat(cli)!: add a review policy every reviewer reads and require --important on a block` (`cefb9ac`)

Commit `cefb9acd870f6f43486366217638663014366118`.

### What changed

`REVIEW.md`, or the path in `reviews.policy`, is now the policy every reviewer reads: the passes
to make, what counts as important, what is a nit and what not to review. `sdlc init` writes it,
`sdlc doctor` reports it, and `sdlc review list` names it. The file and shell rules hold it from
every agent, and the landing refuses a story that changes it. `sdlc review add` takes
`--important` and `--nits`, and a `block` with no `--important`, or 0, is refused with
`SDLC-E0086`. The shell rules also change: a redirect with no command, the `vi` family of
editors, a target assigned on the same line and a comment ending in a backslash with more after
it are now refused or read, so a command that passed before can be refused.

### Steps

1. Add a `REVIEW.md` at the repository root and commit it on trunk, between stories. `sdlc init`
   writes one in a new project, and the `REVIEW.md` in the sdlc repository is an example. Or set
   `reviews.policy` to the path of a file you already keep. Without a file, reviewers review as
   they did.
2. Change any script that records a block so it counts the important findings, for example
   `sdlc review add design_review architect block --important 1`. A review with only nits is an
   `approve` with `--nits`.
3. Update the plugin: its reviewers and runbook pass the new flags.

### Verify

```console
$ sdlc doctor
$ sdlc review add design_review architect block
```

`doctor` exits 0 and reports the review policy. On a story at that gate, the second command is
refused with `SDLC-E0086` and records nothing.

## `feat(cli)!: record every review finding and refuse a gate while one is open` (`ed45983`)

Commit `ed45983614a13d5a8f2bc4c9ce3c6d0d8c149111`.

### What changed

`sdlc review add` takes `--finding "<important|nit> <path>: <text>"` once for each finding, and
the counts must agree with the findings listed (`SDLC-E0089`). `sdlc finding close <gate> <role>
F-n` closes one as `--fixed`, `--declined` or `--referred`, the last two with `--reason`
(`SDLC-E0090`), and a referral of a file the story changed is refused (`SDLC-E0091`). The
verification and commit gates refuse while a design or code review finding is open
(`SDLC-E0092`), and refuse a record whose findings an older `sdlc` dropped (`SDLC-E0093`).
`sdlc status` and `sdlc log` show the ledger.

### Steps

1. Nothing to change in the configuration. Update the plugin: its agents list findings and the
   runbook closes them.
2. In a script that records a review, list each finding with `--finding` so that the count
   given with `--important` and `--nits` matches.
3. For a story in flight with a review that carries a count and no findings, have the reviewer
   record its review again with one `--finding` for each finding it listed (`SDLC-E0093` names
   them).
4. Before the verification and commit gates, close each open finding the refusal names:

   ```console
   $ sdlc finding close code_review code-reviewer F-1 --fixed
   $ sdlc finding close design_review architect F-2 --declined --reason "step 4 covers it"
   ```

### Verify

```console
$ sdlc status
$ sdlc gate verification pass
```

`status` shows each finding as open or closed. The gate passes once none from the design or code
review is open, and until then is refused with `SDLC-E0092`, naming each finding and how to close
it.

## `feat(team)!: configure every agent in one team section` (`a0456a7`)

Commit `a0456a77e534ba63e1bfedd6ac004bb6bb8d79cc`.

### What changed

One `team` section now configures every agent. `team.retries`, `team.models` and `team.efforts`
hold what all agents share, and `team.agents.<agent>` holds `enabled`, `instances`, `lowest`,
`bring_back` and, for a reviewer, `can_block`. The `staffing` section and `"gate7_advisory":
true` in `reviews` are refused by every command that loads the file with `SDLC-E0087`, which
names each old key and its replacement; `"gate7_advisory": false` is a leftover that loads, and
`sdlc doctor` reports it. A team that cannot be used, such as an agent named twice, is refused
with `SDLC-E0088`. The project manager now staffs every story unless the team turns it off.

### Steps

Edit `.sdlc/config.json` on trunk, commit it there, and only then update the binary and the
plugin. A story cannot carry the edit, and every command, `sdlc stop` included, refuses while the
file holds an old key. Move each old key as follows:

| Before | After |
| --- | --- |
| `"staffing": {"enabled": true}` | delete it: the project manager is on by default |
| `"staffing": {"enabled": false}` | `"team": {"agents": {"project-manager": {"enabled": false}}}` |
| `"staffing": {"models": [...]}` | `"team": {"models": [...]}` |
| `"staffing": {"efforts": [...]}` | `"team": {"efforts": [...]}` |
| `"staffing": {"lowest": {"verifier": {...}}}` | `"team": {"agents": {"verifier": {"lowest": {...}}}}` |
| `"staffing": {"bring_back": {"security": [...]}}` | `"team": {"agents": {"security": {"bring_back": [...]}}}` |
| `"reviews": {"gate7_advisory": true}` | `"team": {"agents": {"code-reviewer": {"can_block": false}}}` |
| `"reviews": {"gate7_advisory": false}` | delete the line |

Delete the whole `staffing` section once its keys have moved: an empty `"staffing": {}` is still
refused. Keep `reviews.policy` where it is. For example:

```json
"team": {
  "models": ["haiku", "sonnet", "opus"],
  "agents": {
    "verifier": { "lowest": { "model": "sonnet", "effort": "high" } },
    "security": { "bring_back": ["internal/auth/"] },
    "code-reviewer": { "can_block": false }
  }
},
"reviews": { "policy": "REVIEW.md" }
```

With a story already in flight, follow case 3 of
[Upgrading from the staffing section](../configuration.md#upgrading-from-the-staffing-section).

### Verify

```console
$ sdlc doctor
$ sdlc staffing show
$ sdlc status
```

`sdlc doctor` exits 0, `sdlc staffing show` lists every enabled agent with the project manager's
staffing where it is on, and `sdlc status` shows a story in flight with its next gate.
