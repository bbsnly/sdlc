## Introduction

This guide takes a project that runs `sdlc` 0.5.0 to 0.6.1. There is no 0.6.0
release, so 0.6.1 is the next one up.

Four things change that you will meet straight away:

- Every agent is configured in one `team` section. The `staffing` section it
  replaces is refused.
- Reviewers list each thing they want changed as a finding, and every finding
  is answered before the commit.
- A plain `/sdlc:next` starts only a story you marked `ready`.
- `sdlc parallel` is gone.

Most projects have one or two small edits to make. You make them on trunk, in
your main checkout, between stories, because
[no story lands a change](../configuration.md#changing-a-setting) to
`.sdlc/config.json` or to the backlog.

## Before you update

Three old settings decide how much there is to do. Look for them in your
configuration, from the root of your project:

```console
$ grep -nE '"(staffing|parallel|gate7_advisory)"' .sdlc/config.json
```

What you do next depends on what it prints:

| It prints | What to do |
| --- | --- |
| nothing | Go straight to [Update the command and the plugin](#update-the-command-and-the-plugin). |
| only a line with `"gate7_advisory": false` | The same. The setting now does nothing, so delete it when you next edit the file. |
| `"staffing"`, or `"gate7_advisory": true` | Follow the steps below, in order, before you update. |
| `"parallel"` | [Remove the section](#remove-the-parallel-section), before or after you update. |

> [!WARNING]
> Make the `staffing` and `gate7_advisory` edits before you update. Once the
> new `sdlc` is installed, every command
> [refuses your configuration](../troubleshooting.md#sdlc-e0087) until they
> are made, so no story can land in the meantime.

### Land the stories under way

Finish each story that is under way, and land it, with the `sdlc` you have. A
story under way keeps the configuration it started with, and bringing it onto
an edited one afterwards takes
[several steps of your own](#if-you-updated-first).

### Move your agent settings to `team`

Next, open `.sdlc/config.json` and move each old setting to its new place:

| Before | After |
| --- | --- |
| `staffing.enabled` set to `true` | nothing: the project manager is on by default |
| `staffing.enabled` set to `false` | `enabled` set to `false` in `team.agents.project-manager` |
| `staffing.models` | `team.models` |
| `staffing.efforts` | `team.efforts` |
| `staffing.lowest`, an entry for each agent | `lowest` in that agent's own entry, such as `team.agents.verifier.lowest` |
| `staffing.bring_back`, an entry for each agent | `bring_back` in that agent's own entry |
| `reviews.gate7_advisory` set to `true` | `team.agents.code-reviewer.can_block` set to `false` |
| `reviews.gate7_advisory` set to `false` | nothing: delete the line |

Then delete the whole `staffing` section, because an empty `"staffing": {}`
is still refused. Let's say your file set the models a staffing may ask for,
a floor under the verifier, the paths that bring the security reviewer back,
and an advisory code review. It now has this:

```json
"team": {
  "models": ["haiku", "sonnet", "opus"],
  "agents": {
    "verifier": { "lowest": { "model": "sonnet", "effort": "high" } },
    "security": { "bring_back": ["internal/auth/"] },
    "code-reviewer": { "can_block": false }
  }
}
```

An agent you do not name keeps every default.
[`team`](../configuration.md#team) describes each setting.

Now commit the edit on trunk:

```console
$ git add .sdlc/config.json
$ git commit -m "Move the agent settings to the team section"
```

The `sdlc` you still have does not know `team`, so its `sdlc doctor` reports
a setting it does not know. That clears once you update, so edit and update in
one sitting.

Don't reach for `sdlc init --force` here. It writes the whole configuration
back at its defaults, your commands included.

### Remove the `parallel` section

Delete the `parallel` section from `.sdlc/config.json`, and commit that on
trunk too. Left in place it changes nothing, but `sdlc doctor` reports it as a
setting it does not know and counts it as a problem.

The command went with the section. To work several stories at once, name each
one: type `/sdlc:next <ID>` in a session opened in your project, or run
`sdlc start <ID>` and open a session in the worktree it makes.
[Working several stories at once](../the-loop.md#working-several-stories-at-once)
shows how.

## Update the command and the plugin

Update both parts together. An old command beside the new plugin does not
know the new flags, and
[refuses them](../troubleshooting.md#sdlc-e0034).

First the command, in a terminal:

```console
$ npx @bbsnly/sdlc@latest install
```

Then the plugin, in Claude Code:

```text
/plugin update sdlc@sdlc
```

Restart Claude Code, so that it loads the plugin's new hooks.
[Updating](../installation.md#updating) covers a command you installed
another way.

> [!NOTE]
> Both lines bring you the newest release, which may be later than 0.6.1. If
> `sdlc version` names a later one, read
> [Migrating from v0.6.1 to v0.7.1](v0.6.1-to-v0.7.1.md) as well, before you
> start your next story.

## After you update

With the new `sdlc` installed, two things are left to do in your project. Do
both on trunk.

### Mark your next stories ready

A plain `/sdlc:next`, or `sdlc start` with no story named, used to take a
`todo` story as readily as a `ready` one. It now takes only a `ready` story.
`todo` means the criteria are not settled yet.

In your backlog, set `"status": "ready"` on each story whose criteria are
settled and that you want worked next, and commit the change. To see what
would start, run:

```console
$ sdlc story list
```

The story marked `>` is the one that starts next. With only `todo` stories
left, there is no mark, and `/sdlc:next`
[finds nothing to start](../troubleshooting.md#sdlc-e0010): it says how many
`todo` stories it passed over and names up to five.

You may still start a `todo` story by naming it, with `/sdlc:next <ID>` or
`sdlc start <ID>`. Picking up a story that is already under way works as it
did.

### Add a review policy

Every reviewer now reads one file before anything else: `REVIEW.md`, at the
root of your repository. It says what counts as important, what is only a
nit, how many nits a review may report, and what is not worth reviewing.

`sdlc init` writes the file for a new project. Yours was set up before there
was one, so write it by hand. The
[`REVIEW.md` in the sdlc repository](https://github.com/bbsnly/sdlc/blob/main/REVIEW.md)
is one to start from: keep its headings, and put your own project's rules
under them. Then commit it on trunk.

You may skip this step. Without the file, reviewers review as they did, and
`sdlc review list` says the project has `no review policy`. To keep the file
somewhere else, name it in
[`reviews.policy`](../configuration.md#reviewspolicy).

No agent may write the policy, and no story lands a change to it.
[The review policy](../the-loop.md#the-review-policy) says why.

## What behaves differently

None of these needs an edit. They are here so that nothing surprises you in
your next story.

### The project manager staffs every story

Under 0.5.0 the project manager took part only where you turned the staffing
on. It is now on by default. Before the work starts, it says which agents the
story needs and the model and effort each is asked for, so a small story may
leave a reviewer out. [The staffing](../the-agents.md#the-staffing) explains
how it chooses, and `sdlc staffing show` prints its choices for a story.

To keep things as they were, with every agent in every story, turn it off:

```json
"team": {
  "agents": {
    "project-manager": { "enabled": false }
  }
}
```

### Reviews list their findings

A reviewer now records each thing it wants changed as a numbered finding,
`F-1`, `F-2` and so on, and says whether it is important or a nit. Two rules
follow:

- **A block names something important.** A review that found only nits is an
  approval, with the nits listed.
- **Every finding is answered before the commit.** The loop closes each one
  as fixed, as declined with a reason, or as referred to you. Until it has,
  [Gate 6 and the commit wait](../troubleshooting.md#sdlc-e0092).

The loop does all of this for you. You will see it in `sdlc status`, which
lists each open finding of the story under way:

```text
  finding    design_review architect F-1 open, important: the plan: AC-2 has no step
```

Once a story has landed, `sdlc log` keeps every finding, with how it was
closed. A finding referred to you is yours to read when the story ends.
[The scout rule](../the-loop.md#the-scout-rule) describes the three ways of
closing one.

If you record a review yourself, as when you
[do an agent's gate by hand](../the-agents.md#doing-an-agents-gate-by-hand),
count the findings and list each one:

```console
$ sdlc review add design_review architect block --important 1 \
    --finding "important the plan: AC-2 has no step" < review.md
```

Then close each one with
[`sdlc finding close`](../commands.md#sdlc-finding-close-gate-role-f-n) once
it is dealt with.

### A reviewer asked again reads what changed

When a plan is revised, the reviewers who approved the old one look again.
Each now reads what changed since its own last review, with
`sdlc artifact diff plan --since <reviewer>`, and not the whole plan a second
time. `sdlc review list` names the revision a stale review read.

A story that was under way when you updated has one round in which a reviewer
[reads the whole plan](../troubleshooting.md#sdlc-e0084) instead. Nothing is
wrong with the story.

### More shell commands are refused

The hook reads more of each shell command before it decides, so a command
your agent ran freely under 0.5.0 may now be refused. Each refusal says what
to do instead, and
[Why was I refused?](../guides/why-was-i-refused.md) shows how to read one.

## Settings you may want to add

Two settings are new. Both are off until you add them, and both go in
`.sdlc/config.json`, on trunk.

### Check the tests before they are frozen

`commands.freeze_check` is a command that `sdlc freeze` runs first, with the
test files a story adds or changes named in `SDLC_FREEZE_FILES`. Use it for
what CI would refuse in a test file, such as its formatting or a secret in
it. Found after the freeze, the same mistake costs an unfreeze, and that is
yours to give.

```json
"commands": {
  "freeze_check": "sh scripts/freeze-check.sh"
}
```

The check only reads. One that fails, or that rewrites a test file,
[refuses the freeze](../troubleshooting.md#sdlc-e0085). It runs with your
permissions and without a prompt, so read the one in a repository you did not
write. [The freeze check](../configuration.md#the-freeze-check) has a script
to start from, and says why a check over the whole project does not work
here.

### Hear when a gate runs long

`budget.gate_hours` gives a gate a number of hours of the agents' time:

```json
"budget": {
  "per_story_usd": 60,
  "gate_hours": { "tests_frozen": 2, "implementation": 3 }
}
```

Once a gate is past its number, `sdlc gate`, `sdlc review add` and
`sdlc status` each print one more line saying so. Nothing is blocked. To
silence it, set that gate's number to `0` or take the entry out.
[`budget`](../configuration.md#budget) lists the gate names it takes.

The new `sdlc trace <ID>` shows how long each gate of a story took, which is
where to find a sensible number.

## If a script reads sdlc's output

Check these if you have a script, a CI job or a habit built on what `sdlc`
prints:

- **`sdlc start`** with no story named exits 1 where only `todo` stories are
  left.
- **`sdlc parallel`** is an unknown command, and exits 1.
- **`sdlc review add`** refuses a `block` with no `--important`, or with `0`.
  At the design and code reviews, the `--finding` flags have to match the
  counts.
- **`sdlc review list`** begins with a line naming the review policy. A stale
  design review names the revision it read, and `--json` gives it as
  `reviewed_subject`.
- **`sdlc status`** and **`sdlc log`** gain lines for findings. `sdlc status`
  also names each agent your team turns off, with `disabled` in `--json`.
  After three stories have finished it ends with a line suggesting
  `/sdlc:consolidate`, which
  [`consolidate.nudge_after`](../configuration.md#consolidate) sets.
- **`sdlc doctor`** gains a `review policy` and a `freeze check` line, and
  names the code `SDLC-E0045` beside a setting it cannot use. It no longer
  reports a shell builtin in one of your commands, such as `wait` or `local`,
  as a program that is not installed.

## If you updated first

If the new `sdlc` is already installed and your configuration still has
`staffing`, or `"gate7_advisory": true`, every command refuses, `sdlc stop`
among them. The refusal names each old setting and where it goes.

Nothing is lost. [Move the settings](#move-your-agent-settings-to-team) on
trunk, in your main checkout, and commit. With no story under way, that is
all.

A story under way has its own copy of the file in its worktree. Leave that
copy alone, because an edit there only moves the refusal to the landing.
Bring the story onto the new trunk instead:
[Upgrading from the staffing section](../configuration.md#upgrading-from-the-staffing-section)
gives the commands, in order.

## Check it worked

First, make sure the command is the new one, in a new terminal:

```console
$ sdlc version
```

Then check your project, from its root:

```console
$ sdlc doctor
```

Its last line reads `Everything checks out.` If it names a `parallel` setting
it does not know, or the leftover `reviews.gate7_advisory`, delete that
setting and run it again.

Last, see that a story can start:

```console
$ sdlc story list
```

One story is marked `>`. Type `/sdlc:next` in Claude Code, and it begins.
